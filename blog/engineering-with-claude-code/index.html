How I build with AI coding agents every day

A DevOps engineer's working notes on using Claude Code and agent tooling for real infrastructure work: what to hand over, what to keep, and the guardrails that matter.

Mohammad Efazati17 Nov 2026 · 2 min read

Most of the code I ship today is written with an AI coding agent in the loop. EasyEnv itself is engineered with Claude Code, and its AI features are built on the Anthropic API and Agent SDK. After a lot of hours with these tools on real infrastructure, here is how I use them, and where I do not.

Hand over the typing, keep the judgement

Agents are excellent at the parts of the job that are mostly typing: wiring a new endpoint through four layers, writing the tests for a function you have already designed, converting a shell script into a proper tool, reading a long log and pointing at the interesting line.

They are much weaker at deciding what should exist. Architecture, the boundary between two services, what to monitor, what not to build: those stay with me. The agent works best when I have already decided the shape and it fills it in.

Context is the real skill

The single biggest difference between a useful session and a frustrating one is context. A short project file that says how to build, test and deploy, what the house rules are, and what went wrong last time, saves more time than any prompt trick. When an agent repeats a mistake, the fix is usually to write the lesson down where it will be read next time, not to correct it again in chat.

Guardrails for infrastructure work

Infrastructure is where an agent's confidence is most dangerous, because the blast radius is real. The rules I hold to:

  • Nothing irreversible without a human. Deleting data, force-pushing, touching production: the agent proposes, I approve.
  • Tests before trust. A change is not done because the agent says so; it is done when the tests and the health check say so.
  • Verify every "does not exist". Agents and review bots will tell you a function is missing or a file is unused. Check before you act on it.
  • Deploy from one place. Many agents working at once on one codebase need the same discipline as many people: branches, commits, and one blessed path to production.

Where it changed my work most

The surprise was not speed on big features. It was how much small, useful work now gets done that never would have: the internal tool that saves ten minutes a day, the migration script with proper tests, the dashboard nobody had time for. The cost of "it would be nice if" dropped close to zero.

What this means for hiring

If engineers work like this, interviews should let them. That is a large part of why EasyEnv lets candidates use AI and records the whole session: the skill worth measuring now is how well someone directs and checks the machine, not whether they can type the answer from memory.
